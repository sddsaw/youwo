# Vue 3 + TypeScript + Tauri 全仓架构审查

## 审查结论

审查范围为当前仓库的完整工作区，包含 `apps/admin`、`apps/tauri-app`、`packages/*`、`internal/*` 及 Tauri Rust 工程；未提交修改被作为当前代码状态的一部分观察，但没有将其当作唯一审查范围，也没有修改或回滚任何业务代码。

总体结论：**Request Changes**。仓库已经具备可持续演进的基础，但在凭证管理、版本一致性和桌面权限边界上存在发布前必须处理的风险；Web 与桌面端的大量复制也会持续放大维护成本。

## 已验证结果

- `pnpm typecheck`：通过，13 个任务成功。
- `pnpm lint`：0 error，10 个 warning，主要集中在 `packages/utils` 的文件处理和 analytics 日志代码。
- `pnpm turbo run build`：通过，admin 与 tauri build 均成功。
- `cargo check --locked`：通过。
- 当前两端约有 170 个同路径源码文件，其中 152 个内容完全一致，重复范围覆盖 router、store、service、layout、view 和 hooks。

## 高优先级问题

### 🔴 P0：Apifox Token 硬编码进前端源码

证据：

- `apps/admin/src/service/request/index.ts:16`
- `apps/tauri-app/src/service/request/index.ts:16`

两个入口都把 `apifoxToken` 写成字面量。它会进入 Git 历史、构建产物和桌面安装包，不能视为秘密。

建议立即确认该 token 的用途并轮换；短期改为构建时环境变量，长期将需要权限的调用移到后端代理。增加 secret scanning 和提交前检查，防止同类凭证再次进入源码。

### 🔴 P0：版本源分裂，发布和自动更新可能失配

证据：

- `package.json`、`apps/admin/package.json`、`apps/tauri-app/package.json` 当前为 `2.3.1`。
- `apps/tauri-app/src-tauri/tauri.conf.json:4` 和 `apps/tauri-app/src-tauri/Cargo.toml:3` 仍为 `0.1.0`。
- `apps/tauri-app/src/services/updater/index.ts:9` 的 Web fallback 仍为 `0.1.0`。
- `packages/scripts/src/commands/release.ts` 只更新 `**/package.json`，不会更新 Cargo/Tauri 版本。

这会造成安装包版本、运行时 `getVersion()`、latest.json 和 release tag 之间不一致，带来重复更新提示、降级判断错误和排障困难。

建议建立单一版本源，在 release 命令中同步 `package.json`、`tauri.conf.json`、`Cargo.toml` 和 updater 元数据；CI 增加版本一致性校验，并用真实运行时版本替代硬编码 fallback。

### 🔴 P0：Tauri Capability 与 CSP 仍然过宽

证据：`apps/tauri-app/src-tauri/capabilities/default.json:4-40` 将 `main` 和 `sub-window` 绑定到同一组权限，包含 `fs:default`、`shell:default`、`updater:default`、`deep-link:default`、`global-shortcut:default` 等；`tauri.conf.json` 的 `connect-src` 和 `img-src` 允许任意 HTTPS 来源。

建议按窗口拆分 capability，并只声明实际使用的 `allow-*` 权限。`sub-window` 默认只保留渲染所需的 window/event 能力；文件、shell、更新、全局快捷键和 deep-link 按功能单独授予。CSP 将 API、静态资源和图片域名改为明确白名单，外部链接继续交给系统浏览器处理。

## 重要架构问题

### 🟡 P1：Web 与 Tauri 复制业务层，边界不清

两个应用复制了大部分路由守卫、认证与主题 store、请求层、布局和页面。现在修改一个业务规则需要同步两份代码，容易出现权限、缓存和错误处理漂移。

建议新增 `packages/app-core`，承载领域类型、API client、业务 store、路由元数据和纯业务 composable；新增 `packages/platform-contract` 定义 storage、window、notification、logger、update、event 等端口。`apps/admin` 只提供 Web adapter，`apps/tauri-app` 只提供桌面 adapter，入口层负责组装。迁移按 feature 逐步进行，不要一次性重写全部页面。

### 🟡 P1：桌面能力未完全收敛到 adapter/service

`apps/tauri-app/src/views/desktop/index.vue:25` 直接动态导入 dialog、notification 等 Tauri plugin，`apps/tauri-app/src/App.vue:17` 直接注册 `open-settings` 监听；已有 `src/services/ipc` 和 `src/services/events`，但覆盖不完整。

建议页面只依赖 `DesktopPort` 或 composable，所有 Tauri import、事件监听和错误映射集中在 platform adapter。这样 Web 端可以使用浏览器实现，桌面端可以替换原生实现，也便于单元测试。

### 🟡 P1：`@sa/utils` 已承载业务基础设施

`packages/utils/package.json:25` 依赖 Sentry、TOS SDK、axios、crypto 等，`packages/utils/src/index.ts` 直接导出 analytics、object storage、sentry、storage。任何依赖基础工具的包都会被传递这些大型 SDK 和运行时职责。

建议拆为 `@sa/shared-utils`、`@sa/storage`、`@sa/observability`、`@sa/object-storage`。纯函数包保持无副作用、无网络 SDK，业务基础设施由 app-core 或具体 feature 显式依赖。

### 🟡 P1：`@sa/components` 不是纯 UI 包

`packages/components/package.json:33` 依赖 `@sa/hooks`；`packages/components/src/business/FileUpload/index.vue:5` 直接创建 `ObjectStorageUploader`，RichEditor 也依赖 OBS 配置。组件因此绑定具体云厂商和业务上传策略。

建议将基础组件与 feature components 分包。上传组件通过 `uploader` provider/adapter 和类型化 props 注入，组件只负责文件选择、进度和交互，不直接依赖 TOS SDK。

### 🟡 P1：目录按技术类型组织，领域边界弱

当前 API、store、hooks、views 分散在各自技术目录；一个业务变更需要跨多个目录，且还要同步 Web/Tauri 两份。

建议新功能采用 `features/<domain>` 组织，例如 `features/system-user/{api,model,store,components,views}`；共享的基础 UI 和平台能力留在 packages。旧目录不必一次性迁移，可在新增或大改功能时逐步收敛。

## 中低优先级问题

### 🟢 P2：Updater 类型契约不完整

`apps/tauri-app/src/services/updater/index.ts:9,63,72` 使用多个 `any`，更新句柄和进度事件没有稳定的类型边界。建议使用 Tauri updater 官方类型或定义 `UpdateHandle` 与 `DownloadEvent` 的 discriminated union，并对进度事件做运行时保护。

### 🟢 P2：IPC 错误丢失结构

`apps/tauri-app/src-tauri/src/error.rs:20` 将 `AppError` 序列化成单一字符串，前端无法按错误码、类别或可恢复性处理。建议返回 `{ code, message, details? }`，前端统一映射为 `IpcError`，日志保留原始错误链。

### 🟢 P2：IPC 参数校验不足且错误被忽略

`apps/tauri-app/src-tauri/src/commands/window.rs:12` 只对白名单 label 做校验，`width`、`height` 没有限制，URL 只做 `starts_with` 判断；同文件和 `src-tauri/src/lib.rs` 中多处 `let _ = window.show()`、`let _ = app.emit(...)` 忽略错误。建议使用结构化 DTO、协议/路径校验和尺寸范围，并至少记录 warn/error；关键操作应将失败返回前端。

### 🟢 P2：事件监听生命周期存在竞态

`apps/tauri-app/src/services/events/index.ts:45` 异步注册 Tauri listener，组件卸载与注册完成之间存在竞态；`App.vue` 又绕过该服务直接监听。建议统一事件总线，返回可 await 的 disposer，并让根组件也使用同一 composable/service。

### 🟢 P2：缺少关键自动化测试

至少补充认证 token refresh 并发、route guard 权限矩阵、storage adapter、Tauri IPC contract/mock、Web/Tauri 双入口 smoke test，以及登录、权限、更新提示等关键 Playwright 流程。测试应先覆盖平台边界和共享 core，再覆盖页面细节。

### 🟢 P2：可观测性与隐私配置需明确

`packages/utils/src/business/sentry.ts:42` 将 Session Replay 配置为 `maskAllText: false`、`blockAllMedia: false`。需要确认生产页面是否可能出现个人信息或业务数据；建议默认脱敏，桌面端默认关闭 replay，按环境和页面显式 opt-in，并对用户标识、上传文件名和 URL 参数做过滤。

## 建议建设路线

### P0：发布前完成

1. 轮换并移除硬编码 token，加入 secret scanning。
2. 统一版本源，同步 package、Cargo、Tauri 配置、release tag 和 updater metadata。
3. 拆分 capability，收紧 CSP，明确每个窗口的最小权限。

### P1：一个迭代内完成

1. 建立 `app-core` 与 `platform-contract`，先迁移 auth、request、storage、notification、update。
2. 将 Tauri plugin import 从页面移入 adapter/service，并统一事件订阅和 IPC 错误模型。
3. 把上传、Sentry、analytics 从 `@sa/utils`/`@sa/components` 中拆出显式依赖。
4. 为共享 core 和两个应用入口补齐最小测试矩阵。

### P2：持续治理

1. 新功能采用 feature/domain 目录，逐步收拢旧技术目录。
2. 将 lint warning 逐步清零，并设置 warning budget，避免真实问题被噪音掩盖。
3. 在 CI 固化 typecheck、lint、build、cargo check、版本校验、依赖审计和桌面打包 smoke test。

## 推荐目标目录

```text
packages/
  app-core/             # 领域类型、API、业务 store、路由元数据
  platform-contract/    # storage/window/update/event/logger 端口
  shared-utils/         # 纯函数和无副作用工具
  observability/        # Sentry、analytics、日志适配
  object-storage/       # TOS/OBS 等上传实现
apps/
  admin/                # Web 入口、Web adapter、Web-only 页面
  tauri-app/            # Tauri 入口、Rust commands、desktop adapter
```
